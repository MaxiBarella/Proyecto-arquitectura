# ADR-003: Vuelos y Pistas guardan en MySQL y Clima en MongoDB, con una instancia de base por servicio

- **Fecha:** 7/10/2026; completado el 8/10/2026 con el almacenamiento de Usuarios y las librerías de acceso
- **Estado:** Aceptado; validado el 23/10/2026 con Vuelos, Pistas y Clima funcionando
- **Decisión del enunciado:** D3
- **Reemplaza a:** ninguno

## Contexto

El enunciado (2.8) pide que cada servicio elija el almacenamiento que mejor responde a cómo usa sus datos, que el sistema tenga al menos uno relacional y uno no relacional, y que exista una operación que no pueda duplicar ni perder información. En nuestro sistema esa operación es la asignación de un slot (RN-04, RN-10). Además, cada servicio es dueño de sus datos (ADR-001), así que había que decidir también cuánto se aíslan las bases entre sí.

## Alternativas evaluadas

| Alternativa | A favor | En contra |
|---|---|---|
| **Tipo por servicio.** Vuelos y Pistas relacional; Clima no relacional *(elegida)* | Los slots quedan protegidos por restricciones de la base. Las observaciones de clima son muchas, sin relaciones entre sí y con forma que puede variar según la fuente. Una sola tecnología no relacional para aprender. | Vuelos y Pistas usan el mismo tipo, aunque cada uno con su base. |
| **Tipo por servicio.** Pistas relacional; Vuelos y Clima no relacional | Cada vuelo es un documento completo, cómodo para mostrar en el tablero. | Los vuelos tienen estados y transiciones que se controlan mejor con una estructura fija. Costaba justificar el vuelo como documento. |
| **Aislamiento.** Instancia separada: un servidor de base por servicio *(elegida)* | Aislamiento físico: si se cae una base, las otras siguen. Ningún servicio puede ver datos ajenos. | Más contenedores y más memoria en el arranque local. |
| **Aislamiento.** Esquema separado en un mismo servidor | Cada servicio sigue siendo dueño de lo suyo, con menos consumo. La materia lo describe como aislamiento lógico fuerte. | Si ese servidor se cae, se caen los datos de todos los servicios que lo usan. |
| **Aislamiento.** Base compartida | Lo más simple de armar. | La materia lo trata como antipatrón. Rompe la propiedad de los datos y contradice el ADR-001. |
| **Motor relacional.** MySQL *(elegida)* | Es el que el equipo ya usó en el proyecto de Desarrollo de Software. | Los ejemplos del teórico usan PostgreSQL. |
| **Motor relacional.** PostgreSQL | Es el de los ejemplos del teórico. | El equipo no lo usó en un proyecto propio. |
| **Motor no relacional.** MongoDB *(elegida)* | Se usó en el práctico de la clase 2. Guarda documentos, que es la forma de una observación de clima. | Sin un esquema pensado y sin índices, las consultas se degradan (riesgo que marca la clase 2). |
| **Motor no relacional.** Cassandra | Pensada para mucho volumen de escrituras. | No se vio en la materia y el volumen del proyecto no la justifica. |
| **Usuarios.** MySQL, instancia propia *(elegida)* | Un usuario tiene forma fija y un nombre que no se puede repetir: la base lo impide con una restricción única. Es el motor que ya usan Vuelos y Pistas. | Un servidor de base más en el arranque local. |
| **Usuarios.** MongoDB | Ya está en el sistema por Clima. | Nada en los datos de un usuario pide un modelo de documentos. |
| **Usuarios.** Un esquema dentro del MySQL de otro servicio | Un contenedor menos. | Contradice la instancia separada elegida para el resto. |
| **Acceso a MySQL.** GORM *(elegida)* | El equipo lo usó en el proyecto de Desarrollo de Software. Maneja transacciones y restricciones. | Esconde el SQL: hay que revisar qué consultas genera en la operación crítica. |
| **Acceso a MySQL.** `database/sql` sin ORM | Control total del SQL. | Más código repetido para lo mismo. |

## Decisión

Lo que no se puede duplicar ni perder va en una base relacional, y lo que llega en volumen y sin relaciones va en una no relacional. Cada servicio levanta su propio servidor de base y ninguno lee ni escribe la base de otro.

| Servicio | Almacenamiento | Accesos que tiene que soportar |
|---|---|---|
| Pistas | MySQL, instancia propia | Ocupar un slot (pista más bloque) garantizando que lo tenga un solo vuelo, aun con pedidos simultáneos. Consultar los bloques libres de una pista en un rango horario. Liberar los slots de una pista que se cierra. |
| Vuelos | MySQL, instancia propia | Crear un vuelo y cambiar su estado respetando las transiciones válidas. Leer un vuelo por su identificador. |
| Clima | MongoDB, instancia propia | Agregar observaciones con frecuencia. Leer la última observación de un aeropuerto. |
| Usuarios | MySQL, instancia propia | Buscar un usuario por su nombre al iniciar sesión. Crear usuarios sin repetir el nombre. |

Vuelos, Pistas y Usuarios acceden a MySQL con GORM; Clima usa el driver oficial de MongoDB para Go. En Pistas, que es hexagonal, GORM queda dentro del adaptador de MySQL y el dominio no lo conoce.

Las contraseñas se guardan hasheadas, nunca en texto plano, y no salen en ninguna respuesta.

Estructuras iniciales:

- **Pistas:** tablas de pistas y de slots, con una restricción única sobre pista y bloque; tabla de outbox; tabla de mensajes ya procesados.
- **Vuelos:** tabla de vuelos; tabla de outbox; tabla de mensajes ya procesados.
- **Clima:** colección de observaciones, con índice por aeropuerto y fecha; un documento de aptitud por aeropuerto.
- **Usuarios:** tabla de usuarios, con restricción única sobre el nombre de usuario.

El motor de búsqueda (Solr) y la caché no se cuentan como la base no relacional: guardan copias derivadas, no son fuente de verdad. Se tratan en los ADR-006 y ADR-007.

## Consecuencias aceptadas

- La regla "un slot, un solo vuelo" puede apoyarse en una restricción única de la base sobre pista y bloque, en lugar de depender solo del código.
- En Vuelos y Pistas, el cambio de negocio y el evento pendiente de publicar se pueden guardar en una misma transacción, que es lo que necesita el Transactional Outbox (ADR-005).
- Entre servicios no hay claves foráneas ni consultas cruzadas. Vuelos guarda solo el identificador del slot; Pistas guarda el identificador del vuelo y su tipo de operación. Esos datos se mantienen al día por eventos, así que durante un momento pueden estar desactualizados.
- El arranque local levanta cuatro servidores de base (tres MySQL y un MongoDB), además de Solr, RabbitMQ y la caché. Hay que verificar que las computadoras del equipo lo soporten.
- El equipo opera dos tecnologías de base distintas.

**Validación con el sistema funcionando (23/10/2026).**

Se levantó el Docker Compose completo y se recorrió el flujo principal: una aerolínea publicó un despegue, pidió un slot en la pista `05-23` y el vuelo quedó programado. Después se revisó qué guardó cada base.

- **Confirmado: una instancia de base por servicio.** Corren `mysql-vuelos`, `mysql-pistas`, `mysql-usuarios` y `mongo-clima`, cada una en su contenedor.
- **Confirmado: ningún servicio ve la base de otro.** Vuelos y Pistas se conectan con un usuario propio que solo tiene permisos sobre su base (5.9); `SHOW DATABASES` con el usuario de Vuelos muestra únicamente `vuelos`.
- **Confirmado: "un slot, un solo vuelo" lo garantiza la base.** La tabla `slots` de Pistas tiene una restricción única sobre pista y bloque, y otra sobre el vuelo, que es la que hace idempotente el pedido de slot (ADR-005). El slot del vuelo quedó guardado una sola vez.
- **Confirmado: el outbox va en la misma base que el dato.** Vuelos y Pistas tienen su tabla de outbox y su tabla de mensajes procesados. El evento "slot asignado" se guardó en el outbox de Pistas, se publicó, y Vuelos registró el mensaje como procesado.
- **Confirmado: Clima guarda en MongoDB lo previsto.** La colección `observations`, con índice por aeropuerto y fecha, y un documento de aptitud por aeropuerto con su outbox adentro (4.7).
- **Confirmado: las librerías.** Vuelos y Pistas acceden con GORM; Clima, con el driver oficial de MongoDB.
- **Cambió: cómo se crean las tablas.** Con un script SQL que MySQL corre al crear la base (5.6), no desde el código, para que las dos instancias de Vuelos no compitan por crearlas.
- **Cambió: lo que Vuelos guarda de Pistas.** La pista y el bloque, no un identificador de slot (4.11).
- **Nuevo: las observaciones de Clima se borran solas a los 7 días** con un índice TTL (9.16), porque el servicio solo usa la última.
- **Nuevo: la copia de Clima en Render usa MongoDB Atlas** (9.7), una base distinta de la del Docker Compose. Las dos copias guardan cada una sus observaciones (9.3).

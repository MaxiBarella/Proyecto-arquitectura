# ADR-014: El mismo NGINX del balanceo hace de gateway: verifica el JWT con un script, pasa la identidad en encabezados y limita el tráfico por IP

- **Fecha:** 16/10/2026; construido el 9/11/2026
- **Estado:** Aceptado
- **Decisión del enunciado:** adicional
- **Reemplaza a:** ninguno

## Contexto

El enunciado (2.1) pide un API gateway como punto de entrada único, que resuelva autenticación, direccionamiento y control de tráfico. En la clase 6 se separaron los dos roles: el balanceador elige una instancia sana entre copias iguales, y el gateway decide qué API se expone y bajo qué política. Además, el gateway autentica y cada servicio sigue autorizando sobre sus recursos. Había que elegir con qué se hace, cómo conviven gateway y balanceador, qué token se usa y cómo se verifica, cómo se entera cada servicio de quién pide y cuánto tráfico se deja pasar. El 16/10/2026 el profe respondió que NGINX puede hacer los dos roles, y recomendó dos archivos de configuración, uno por rol.

## Alternativas evaluadas

| Decisión | Alternativa | A favor | En contra |
|---|---|---|---|
| Herramienta (15.1) | **NGINX, el mismo del balanceo** | Ya está para el balanceo (ADR-012): no suma herramientas. | Verificar un JWT es una función de la versión paga: hay que escribir un script. |
| Herramienta (15.1) | Un gateway dedicado, como Traefik o Kong | Traen la verificación del token y el límite de tráfico sin escribir código. | Otra herramienta para aprender y levantar. Habría que dejar NGINX o poner dos proxies en fila. |
| Roles (15.3) | **Un NGINX, dos archivos** | Lo recomendó el profe. Cada rol se lee por separado, en un solo contenedor. | Si NGINX se cae, se caen los dos roles a la vez. |
| Roles (15.3) | Un solo archivo | El profe dijo que se puede. | Las rutas y el token quedan mezclados con las instancias de Vuelos. |
| Token (15.2) | **JWT firmado, que dura 1 hora** | NGINX lo verifica sin preguntarle a Usuarios: si Usuarios se cae, las sesiones abiertas siguen andando. | No se puede anular antes de que venza. |
| Token (15.2) | Una sesión guardada en Usuarios, que el gateway consulta en cada pedido | Se puede cerrar una sesión al instante. | Cada pedido depende de Usuarios: si se cae, se cae todo el sistema. |
| Verificación (15.4) | **Un script con njs, el módulo oficial de NGINX para JavaScript** | Funciona en el NGINX gratuito y no llama a Usuarios. | Es código propio, que hay que probar. |

| Firma (15.5) | **HS256, con una clave compartida (`JWT_SECRET`)** | Lo más simple de verificar desde el script. | Usuarios y NGINX comparten un secreto, y quien lo tenga puede firmar tokens válidos. |
| Firma (15.5) | RS256: Usuarios firma con una clave privada y NGINX verifica con la pública | NGINX no puede firmar tokens. | Un par de claves para generar y repartir, y una verificación más difícil de escribir en el script. |

| Identidad (15.6) | Que cada servicio verifique el token | Ninguno depende del gateway para saber quién pide. | La clave en los cuatro servicios y el mismo código repetido. |
| Sin token (15.18) | **`401 INVALID_TOKEN` en Problem Details** | El mismo formato de error que los servicios. El motivo queda en el log. | El cliente no sabe si el token faltaba, era inválido o venció. |

| Ruta interna (15.19) | **Bloquear `/api/pistas/internal/`** | Una sola regla, y las rutas nuevas pasan sin tocar el gateway. | Hay que acordarse de no poner rutas públicas bajo `/internal` en Pistas. |
| Ruta interna (15.19) | Dejar pasar solo las rutas de los contratos | Lo que no está en un contrato no existe desde afuera. | Cada ruta nueva obliga a tocar el gateway. |
| Servicio caído (15.23) | **`502` o `504` en Problem Details, con `SERVICE_UNAVAILABLE`** | Todos los errores llegan en el mismo formato, y el estado dice si el servicio no está o no contestó a tiempo. | Un código más para el frontend. |
| Servicio caído (15.23) | La página en HTML que trae NGINX | No hay que configurar nada. | El frontend no puede leer el error: muestra un mensaje genérico, sin código. |
| Servicio caído (15.23) | Unificar todo en `503` | Un solo número para "probá de nuevo". | Borra la diferencia entre un servicio caído y uno colgado. |

## Decisión

Un solo NGINX hace de gateway y de balanceador, con un archivo por rol: `gateway.conf` y `balanceo.conf`, en `nginx/` (15.1, 15.3). Usuarios entrega un JWT y NGINX lo verifica en cada pedido con un script njs, sin preguntarle a Usuarios. Después, le pasa a cada servicio quién pide en encabezados. Razón: cumple los tres pedidos del enunciado con la herramienta que ya se usaba, y la caída de Usuarios no corta las sesiones abiertas. El detalle de cada ruta y de cada rechazo está en `nginx/README.md`.

- **Rutas (15.7, 15.19).** `/api/vuelos/`, `/api/pistas/`, `/api/usuarios/` y `/api/clima/` piden un token válido y van al servicio sin el prefijo. Sin token pasan solo `/api/usuarios/login` y `/api/vuelos/board`. `/api/pistas/internal/` da `404`, porque solo la usa Vuelos por adentro. El resto sirve el frontend, desde el mismo origen que la API, así que no hace falta CORS.
- **El token (15.2, 15.5, 15.13, 15.21).** Lleva `sub`, `role` (`airline` u `operator`), `airline` solo para las aerolíneas, `iat` y `exp`, y dura 1 hora. El script (`nginx/jwt.js`) solo acepta HS256, así que no pasa uno con `"alg": "none"`. También rechaza un token con la firma alterada, uno vencido o uno con datos que faltan. `JWT_SECRET` tiene que tener al menos 32 bytes: si es más corta, NGINX no arranca.
- **La identidad (15.6).** NGINX manda `X-User-Id`, `X-User-Role` y, si es una aerolínea, `X-Airline`, y siempre pisa los que mande el cliente con esos nombres. Cada servicio decide qué puede hacer ese usuario: por ejemplo, Vuelos le responde `403` a un operador que quiere publicar un vuelo.
- **Los errores (15.18, 15.23).** Todos en Problem Details, como los de los servicios, que pasan sin cambios. Sin un token válido, `401 INVALID_TOKEN`; el motivo queda en el log de NGINX, en JSON. Con el servicio caído, `502 SERVICE_UNAVAILABLE`, y si no conectó o no respondió a tiempo, `504 SERVICE_UNAVAILABLE`.
- **El control de tráfico (15.8).** 20 pedidos por segundo por IP, con ráfagas de hasta 40. Al pasarlo, `429 RATE_LIMIT_EXCEEDED`. Se sube para las pruebas de carga (ADR-013). Con un solo NGINX no hay que coordinar el límite entre réplicas.
- **Cuánto espera (12.5).** 1 segundo para conectar y 10 para responder, para todos los servicios.

**La excepción: Clima en la nube (9.3, 9.9).** El grupo que consume nuestra API de clima entra directo a la copia de Clima en Render, sin pasar por este gateway. Esa copia resuelve por su cuenta lo que acá hace NGINX: autentica con una clave por grupo en `X-API-Key` (9.5) y limita a 60 pedidos por minuto por clave (9.6). El gateway es la entrada única de nuestros usuarios: aerolíneas, operador y tablero público.

## Consecuencias aceptadas

- Si Usuarios se cae, solo falla el inicio de sesión: los tokens ya entregados siguen sirviendo hasta que vencen.
- Un token no se puede anular. Si alguien lo roba, sirve hasta su vencimiento, como mucho 1 hora. Cerrar sesión en el frontend borra la copia del navegador (22.7), pero el token sigue siendo válido.
- Quien tenga `JWT_SECRET` puede armar tokens de cualquier usuario. La clave está en el `.env` de Usuarios y de NGINX, nunca en el repo.
- Los servicios creen lo que dicen los encabezados. Mientras expongan su propio puerto (8081 a 8084, 15.20), alguien que llegue directo puede mandar cualquier identidad.
- NGINX es la única entrada de nuestros usuarios: si se cae, ellos se quedan sin sistema (también en el ADR-012). La copia de Clima en la nube sigue andando.
- El límite es por IP: varios usuarios detrás de la misma IP comparten el cupo.
- Cuando se cae un servicio, los primeros pedidos esperan 1 segundo y reciben `504`, porque NGINX todavía tiene la dirección del contenedor y no conecta. A los pocos segundos deja de encontrar el nombre y responde `502` al instante.
- Un `502` dice que el pedido no llegó al servicio, y se puede repetir. Un `504` no lo asegura: si NGINX dejó de esperar a los 10 segundos, el servicio pudo haberlo aplicado igual. Repetir un `POST /flights` en ese caso puede dejar el vuelo duplicado (12.8). Por eso el `504` dice "Puede que el pedido se haya aplicado: revisá antes de repetirlo".
- El script es código propio: lo cubre la prueba `nginx/prueba/prueba.sh`.

## Pendiente

- **Resuelto el 9/11/2026: construido y probado.** `nginx/prueba/prueba.sh` levanta el gateway delante de un servicio falso que devuelve lo que le llegó. Corre 38 casos: rutas, identidad, tokens rechazados (vencidos, mal firmados, con `"alg": "none"` o con datos cambiados), la ruta interna, el frontend, el límite (de 80 pedidos de golpe pasan 41 y 39 reciben `429`), el log, la clave corta y el servicio caído. El 10/11/2026 dio 38 de 38. Carola repitió en Windows la versión anterior, sin los casos del servicio caído.
- **Resuelto el 10/11/2026: probado con Usuarios real.**
  - El token trae los cinco datos de la 15.13 y dura 3600 segundos.
  - La aerolínea lista sus vuelos y el operador ve las pistas.
  - El operador que publica un vuelo recibe `403`, y la ruta interna de Pistas da `404`, aun con token.
  - Con Usuarios apagado, la aerolínea siguió usando su token, y el inicio de sesión recibió `504` y `502` en Problem Details.
  - Con el límite normal, de 60 pedidos seguidos, 10 recibieron `429`.
- **Sacar los puertos directos 8081 a 8084 (15.20).** Usuarios ya entrega tokens (#54), así que se cumple la condición. Hay que coordinarlo con el grupo, porque el `README.md` y los contratos de Vuelos, Pistas y Usuarios usan esos puertos, y sin ellos el `/health` de cada servicio no se ve desde afuera.
- **Confirmar con el profe que Clima en la nube puede quedar fuera del gateway** (9.9, pendiente en `docs/ARCHITECTURE.md`).

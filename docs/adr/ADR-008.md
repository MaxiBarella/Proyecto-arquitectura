# ADR-008: La API de Clima se publica como un contrato OpenAPI versionado en la ruta

- **Fecha:** 8/10/2026, completado el 18/10/2026 con las decisiones de publicación de la Entrega 2
- **Estado:** Aceptado
- **Decisión del enunciado:** D8
- **Reemplaza a:** ninguno

## Contexto

El enunciado (sección 4) pide publicar una capacidad para que otro grupo la consuma sin explicaciones privadas, con un contrato formal, versionado y procesable en `docs/contracts/`, un mock para la Entrega 1 y la implementación real en la nube, con URL pública, desde la Entrega 2. La capacidad es Clima: las condiciones actuales de Córdoba y si se puede operar (6.1, 6.9). El consumidor no nos conoce, va a hacer pruebas de carga contra la API, y detrás de Clima hay una fuente gratuita que puede fallar.

## Alternativas evaluadas

| Alternativa | A favor | En contra |
|---|---|---|
| **OpenAPI 3.1, una operación, versión en la ruta (`/v1`)** | Estándar y procesable; el consumidor lo lee con cualquier herramienta y el mock sale del mismo archivo. Un solo pedido trae condiciones y aptitud. La versión se ve en cada URL. | Mantener `/v1` cuando aparezca `/v2` obliga a sostener dos versiones. |
| Dos operaciones (condiciones y aptitud por separado) | Cada respuesta es más chica. | El consumidor necesita dos pedidos para tener todo. |
| Aptitud separada para aterrizar y despegar, o una por pista | Más realista. | Contradice 2.2, 2.4 y 2.5; la aptitud por pista obliga a Clima a conocer datos de Pistas. |
| Clave en `Authorization: Bearer` o en la URL | Bearer es habitual. | Para una clave fija por consumidor no aporta nada; en la URL queda en los logs. |
| Errores con formato propio | Más simple de escribir. | No es estándar; Problem Details (RFC 9457) con un `code` propio deja decidir sin leer textos. |
| Sin límite de pedidos | Nada que implementar. | Las pruebas de carga de otros grupos pueden tumbar Clima y agotar Open-Meteo. |
| Mostrar en la API el clima forzado | El consumidor vería nuestras pruebas. | Le altera sus propias pruebas con datos simulados. |
| **Responder con el último dato guardado, hasta 30 minutos** (9.1, 9.2) | Un corte breve de Open-Meteo no le llega al consumidor. | Pasados 30 minutos responde `503`; antes, el dato puede tener hasta media hora. |
| Consultar Open-Meteo en cada pedido | El dato siempre es el más nuevo. | Cada pedido del consumidor depende de Open-Meteo y le suma su demora. |
| Mock con Mockoon | Tiene interfaz gráfica. | El mock queda en un archivo aparte que hay que mantener; Prism lo genera del contrato. |
| Publicar el mock en la nube | El consumidor prueba sin instalar nada. | Duplica el trabajo de publicar: se publica directamente el Clima real (9.8). |

## Decisión

Se publica una sola operación, `GET /v1/airports/{icao}/conditions`, descrita en [clima-v1.yaml](../contracts/clima-v1.yaml) y documentada en [docs/contracts/README.md](../contracts/README.md). Se autentica con `X-API-Key`, informa los errores en Problem Details indicando cuáles se reintentan, y devuelve siempre datos reales. Los cambios compatibles, como agregar campos, códigos o aeropuertos, no cambian la versión; los que rompen crean `/v2` y `/v1` se mantiene. La razón principal es que el consumidor pueda integrarse y probar errores solo con el contrato.

Para publicarla, Clima corre en Render con MongoDB Atlas (9.4, 9.7), y el consumidor le pega directo, sin gateway (9.9). Responde con la última observación guardada, que se renueva cada 15 minutos, y responde `503` si tiene más de 30 (9.1, 9.2). El límite de 60 pedidos por minuto por clave se cuenta en memoria dentro de Clima, que en la nube corre en una sola instancia (9.6). Las claves se cargan como variable de entorno secreta (9.5). El mock queda en el repo para pruebas locales (9.8).

## Consecuencias aceptadas

- El consumidor tiene todo en un pedido y puede probar cada error con el mock antes de usar el servicio real.
- La API le sirve al consumidor solo si su sistema tiene sentido con el clima de Córdoba.
- El dato puede tener hasta 30 minutos; pasado eso, el consumidor recibe `503` con `Retry-After`.
- Render duerme el servicio sin uso: el primer pedido tarda cerca de un minuto y puede traer un dato viejo o un `503`. Lo absorbe el consumidor con su timeout y sus reintentos, y está avisado en la guía del contrato.
- El límite en memoria solo es correcto con una instancia. Si Clima en la nube escalara a más, habría que contarlo en un lugar compartido.
- La copia de la nube y la del Docker Compose consultan Open-Meteo por separado (9.3), así que durante unos minutos pueden mostrar datos distintos.
- El mock no distingue aeropuertos: los errores 404, 429 y 503 se prueban pidiéndolos con el header `Prefer`.
- Los umbrales simplificados no contemplan el viento cruzado según la orientación de cada pista.

# ADR-008: La API de Clima se publica como un contrato OpenAPI versionado en la ruta

- **Fecha:** 8/10/2026
- **Estado:** Aceptado
- **Decisión del enunciado:** D8
- **Reemplaza a:** ninguno

## Contexto

El enunciado (sección 4) pide publicar una capacidad para que otro grupo la consuma sin explicaciones privadas, con un contrato formal, versionado y procesable en `docs/contracts/`, y un mock para la Entrega 1. La capacidad es Clima: las condiciones actuales de Córdoba y si se puede operar (6.1, 6.9). El consumidor no nos conoce, va a hacer pruebas de carga contra la API, y detrás de Clima hay una fuente gratuita que puede fallar.

## Alternativas evaluadas

| Alternativa | A favor | En contra |
|---|---|---|
| **OpenAPI 3.1, una operación, versión en la ruta (`/v1`)** | Estándar y procesable; el consumidor lo lee con cualquier herramienta y el mock sale del mismo archivo. Un solo pedido trae condiciones y aptitud. La versión se ve en cada URL. | Mantener `/v1` cuando aparezca `/v2` obliga a sostener dos versiones. |
| Dos operaciones (condiciones y aptitud por separado) | Cada respuesta es más chica. | El consumidor necesita dos pedidos para tener todo. |
| Aptitud separada para aterrizar y despegar, o una por pista | Más realista. | Contradice 2.2, 2.4 y 2.5; la aptitud por pista obliga a Clima a conocer datos de Pistas. |
| Clave en `Authorization: Bearer` o en la URL | Bearer es habitual. | Para una clave fija por consumidor no aporta nada; en la URL queda en los logs. |
| Errores con formato propio | Más simple de escribir. | No es estándar; Problem Details (RFC 9457) con un `code` propio deja decidir sin leer textos. |
| Sin límite de pedidos | Nada que implementar. | Las pruebas de carga de otros grupos pueden tumbar Clima y agotar Open-Meteo. |
| Mostrar en la API el clima forzado | El consumidor vería nuestras pruebas. | Le altera sus propias pruebas con datos simulados. |
| Devolver el último dato conocido si Open-Meteo no responde | Más resiliente. | Hay que definir hasta qué antigüedad sirve. Se puede agregar después sin romper el contrato. |
| Mock con Mockoon | Tiene interfaz gráfica. | El mock queda en un archivo aparte que hay que mantener; Prism lo genera del contrato. |

## Decisión

Se publica una sola operación, `GET /v1/airports/{icao}/conditions`, descrita en [clima-v1.yaml](../contracts/clima-v1.yaml) y documentada en [docs/contracts/README.md](../contracts/README.md). Se autentica con `X-API-Key`, tiene un límite de 60 pedidos por minuto por clave, informa los errores en Problem Details indicando cuáles se reintentan, y devuelve siempre datos reales. El mock se genera con Prism a partir del contrato. Los cambios compatibles, como agregar campos, códigos o aeropuertos, no cambian la versión; los que rompen crean `/v2` y `/v1` se mantiene. La razón principal es que el consumidor pueda integrarse y probar errores solo con el contrato.

## Consecuencias aceptadas

- El consumidor tiene todo en un pedido y puede probar cada error con el mock antes de que exista la implementación.
- La API le sirve al consumidor solo si su sistema tiene sentido con el clima de Córdoba.
- Si Open-Meteo no responde, el consumidor recibe `503` y no hay dato de respaldo.
- El límite de pedidos hay que implementarlo y probarlo.
- El mock no distingue aeropuertos: los errores 404, 429 y 503 se prueban pidiéndolos con el header `Prefer`.
- Los umbrales simplificados no contemplan el viento cruzado según la orientación de cada pista.

## Pendiente

- Si el mock se publica en internet antes de la implementación real, y en qué hosting (6.17, 7.2).
- Si el límite de pedidos se implementa en Clima o en el gateway (7.4).
